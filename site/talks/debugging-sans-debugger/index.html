What Is This?

  • Debugging tools & techniques
  • Not: how to use lldb
  • Not: how to use ETW
  • Not: how to debug your specific bug

Some Polemic

  • Write code that can be debugged
  • Yes: pure functions, values, explicit deps
  • No: classes, methods, state, implicit deps
  • Extra no: threads, locks, 3P libraries

The Three Schools

  • Informal Reasoning
  • Formal Reasoning
  • Testing

Formal Reasoning!?

  • Describe system formally
  • Prove implementation matches formal spec
  • Clever theory with greek letters and stuff
  • Correctness proofs, static checking, ...
  • "Beware of bugs in the above code..." - Knuth

Testing

  • Put system in some state & assert stuff
  • CQ tests, waterfalls, ...
  • "Program testing can be a very effective way to show the presence of bugs but is hopelessly inadequate for showing their absence." - Dijkstra

Those Are Lies

  • Formal semantics are no match for reality
  • Testing is no match for state explosion
  • Neither of these are really useful debugging tools(*)
(*): testing can be

Informal Reasoning

  • "x = 1 here... so f(x) is true here"
  • rapidly becomes very hard
  • 7 ± 2 values
  • always your main tool

Expected vs Actual

  • Primary informal reasoning tool
  • "I expected ... but actually ..."
  • "Why?"
  • (repeat)

Root vs Proximate Cause

  • Root cause: what originally went wrong
  • Proximate cause: where did it become obvious
  • Expected/actual connects these
  • So do most of the rest of these!

printf() / LOG()

  • You already use these
  • Tip: make them greppable
  • Inspect the system as it runs
  • "Control got here" markers

printf("bounds: %s\n", ...);

LOG(ERROR) << "X::Y() called";

X::X() { printf("X[%p]::X()\n", this); }
X::~X() { printf("X[%p]::~X()\n", this); }

LOG(ERROR) << "If you see this please ping ellyjones@!";

base::debug::StackTrace

  • ::Print()
  • Reified stack trace!
  • Also, TaskTrace
  • These cost a few KiB each
  • Use as a crash key

base::debug::StackTrace().Print();

X::X() : created_at_(base::debug::StackTrace()) { ... };
void X::OnUse() {
  if (!AreThingsOkay()) {
    created_at_.Print();
  }
}

void X::OnControllerDestroyed() {
  if (pending_task_) {
    LOG(ERROR) << "Pending task outlived controller:";
    pending_task_trace_.Print();
  }
}

CHECK() / DCHECK()

  • Assert your invariants!
  • ... also, documentation
  • Check arguments
  • Check results
  • Check intermediates

WebContents* c = controller->browser()
    ->tab_strip_model()
    ->GetActiveWebContents();

Browser* b = controller->browser();
CHECK(b);
TabStripModel* m = b->tab_strip_model();
CHECK(m);
WebContents* c = m->GetActiveWebContents();
CHECK(c);
...

void X::DoSomething() {
  CHECK(AreThingsOkay());
  ...
}

AreThingsOkay()

  • An invariant is a predicate
  • Make that a function...
  • ... and call it all over

NoExpiredElementsInList();
AtMostOneViewShowing();
PeerSocketIsOpen();
BoundsAreNonEmpty();
ControllerIsStillAlive();

// and then...:
TEST(YourClass, ExpiredElementsRemovedFromList)
TEST(YourClass, SwitchingTabsHidesOldView)

// and maybe...:
TEST(YourClassDeathTest, PeerSocketClosedEarly)
TEST(YourClassDeathTest, EmptyBoundsAtConstruction)
TEST(YourClassDeathTest, ControllerDestroyedPrematurely)

base::SequenceChecker

  • Rarely useful...
  • ... but sometimes crucial
  • Init in your constructor
  • DCHECK_CALLED_ON_VALID_SEQUENCE

*SAN

  • asan: UAF, read/write from/to unallocated memory
  • msan: read from uninitialized memory
  • tsan: data races of various kinds
  • lsan: memory leaks
  • ubsan: undefined behavior of various kinds
  • often a good first resort

--draw-view-bounds-rects

  • Hairline boxes around every View
  • Great for layout problems
  • ... and for overpainting problems
  • ... and for animations

Crash keys

  • Attach data to crashes
  • Last focused view, last executed command...
  • Last call stack trace!?
  • Be PII-careful with these
  • Great for field bugs with no repro

chrome://tracing

  • Check out lots of kinds of perf
  • Add your own: TRACE_EVENT(...)
  • Great for: "where is the time going?"

tools/bisect-builds.py

  • Binary search for first bad revision
  • Can take a script to test against
  • Great for finding a regression range
  • Then: omahaproxy

crash/

  • Find prevalence & common factors
  • What were other threads doing?
  • Great for: field crashes, 3P causes, ...
  • Also: seeing your crash keys!
  • See also: crsym/
